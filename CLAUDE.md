# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Collection of GitHub composite actions for JetHome firmware and package management workflows. The main action is **firmware-upload** — it transforms a dot-separated fullslug (e.g. `JetHome.j100.Armbian.release.bookworm.edge`) into a hierarchical JSON structure and uploads firmware to the fw.jethome.com API.

## Actions

| Action | Purpose |
|--------|---------|
| `firmware-upload/` | Parse fullslug → generate JSON hierarchy → upload firmware to fw.jethome.com |
| `tsa-publish/` | Publish a release to the tsa update server (platform v2): create release → upload artifacts with resume → verify |
| `repo-upload/` | Upload .deb packages to repo via SSH/rsync |
| `repo-upload-json/` | Upload .deb packages using JSON config (debs-to-repo-info.json) |
| `armbian-version/` | Extract Armbian version from stable/nightly.json |
| `armbian-jethome-version/` | Manage JetHome subversion (increment/decrement/zero) |

## firmware-upload Architecture

### Fullslug Format
```
<vendor>.<platform>.<project>[.<subtype1>.<subtype2>...]
```

### Pipeline (action.yml steps)
1. **checkvars** — parse fullslug into vendor, platform, slug; validate date/version
2. **apply-fw-template** — run `python3 main.py <args>` to generate hierarchy JSON, POST to `/api/import_hierarchy/`
3. **add-fw-slot** (optional) — POST to `/api/create_firmware/` when `generatefirmwareslot: true`
4. **deploy-to-fw-storage** — compute SHA256, upload file to `/api/upload_firmware/` with retry (3 attempts, exponential backoff)

Each step's shell lives in `firmware-upload/scripts/<step-id>.sh`; `action.yml` only wires inputs and step outputs into `env:` and calls the script.

### Hierarchy Generator (`generate_hierarchy/`)

`main.py` loads brand/platform/project from JSON templates, then dispatches to a project-specific module:

| Module | Slug aliases | Subtype format |
|--------|-------------|----------------|
| `armbian.py` | armbian | `channel release [clitype] branch` (3-4 subtypes) |
| `firmware.py` | firmware | `fwtype [device] channel` (2-3 subtypes) |
| `generic.py` | magicos, armbianha, jhaos, jhrescueos | `channel` (1 subtype) |
| `burntools.py` | burntools | no subtypes |

Each module exports `generate(subtypes, load_json)` and optionally `ALIAS` list. Templates live in `generate_hierarchy/templates/`.

## Testing

Run hierarchy generator tests (from anywhere):
```bash
bash firmware-upload/generate_hierarchy/tests/test.sh
```

Tests compare `python3 main.py <args>` output against reference files in `tests/`. To add a test case, add a `check_main` call in `tests/test.sh` with a new reference output file. To regenerate golden files: `UPDATE_GOLDEN=1 bash firmware-upload/generate_hierarchy/tests/test.sh`.

Run tsa-publish tests (artifacts parsing, release-info.json, curl resume and API key handling; no server or key needed):
```bash
bash tsa-publish/tests/test.sh
```

Reference output lives in `tsa-publish/tests/golden/`, one file per case; `tsa-publish/tests/fixtures/` holds only inputs longer than three lines, while the fake build tree and short inputs are generated by `test.sh` in a temp directory. To regenerate golden files: `UPDATE_GOLDEN=1 bash tsa-publish/tests/test.sh`.

Run action argv tests (from anywhere):
```bash
bash tests/test_actions.sh
```

These run each composite action step from `<action>/scripts/` with stubbed `curl`, `ssh`, `rsync`, `sha256sum`, `date`, `mktemp` and `sleep` (`tests/stubs/`) and compare the captured argv, uploaded file contents, `GITHUB_OUTPUT`, `GITHUB_ENV` and listed result files against `tests/argv/<scenario>.expected`. Scenarios live in `tests/scenarios/<scenario>.env`. To regenerate a single golden: `UPDATE_GOLDEN=1 bash tests/run_action.sh tests/scenarios/<name>.env`. Where `/bin/bash` is a different major version than `bash` on `PATH` (system bash 3.2 on macOS), every scenario also runs under `/bin/bash`; step scripts must not use bash 4 features such as `mapfile`.

## Code Style

- Python: 4-space indentation (stdlib only, no external dependencies)
- YAML: 2-space indentation
- Shell steps in action.yml use `bash` and only call `<action>/scripts/<step-id>.sh`; inputs reach the script through `env:` as `INPUT_<NAME>` (step outputs as `<STEP>_<OUTPUT>`), never as `${{ }}` inside the script
- Every step script starts with `set -eo pipefail`: the runner runs `shell: bash` with these options, and the script runs in a child bash that does not inherit them
- Step scripts are clean under `shellcheck -S info`
- A new or changed action step needs a scenario in `tests/scenarios/` and its golden in `tests/argv/`; a golden changes only together with an intended behaviour change
- Code comments in Russian

## CI/CD

- All GitHub Actions jobs must use `runs-on: self-hosted` (never GitHub-hosted runners)

## Adding a New Project Type

1. Create `firmware-upload/generate_hierarchy/modules/<slug>.py` with `generate(subtypes, load_json)` function
2. Optionally define `ALIAS = [...]` for alternative names
3. Add entry to `generate_hierarchy/templates/projects.json`
4. Add project-specific templates if needed (e.g. `templates/<slug>/`)
5. Add test cases to `test.sh` with reference output files
